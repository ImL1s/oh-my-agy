# Repository Guidelines

## Project Structure & Module Organization

`bin/oma.ts` is the executable CLI entry point. Core continuation, locking, rollback, and circuit-breaker behavior lives in `src/enforcer.ts`; shared TypeScript contracts live in `src/types.ts`. End-to-end coverage is under `e2e/`: `tier1.spec.ts` through `tier4.spec.ts` group progressively broader scenarios, `helper.ts` manages isolated fixtures, and `mocks/agy` replaces the external CLI during tests. `dist/` is generated by TypeScript; do not edit it directly. Treat `.agy/`, `.omx/`, and `.agy_sandbox_*` as runtime state, not source. Architecture and test rationale are documented in `PROJECT.md` and `TEST_INFRA.md`.

## Build, Test, and Development Commands

- `npm ci` installs the exact dependency versions from `package-lock.json`.
- `npm run build` runs strict TypeScript compilation and writes output to `dist/`.
- `npm run test:e2e` runs every Jest suite serially, avoiding shared-state races.
- `npx jest e2e/tier1.spec.ts --runInBand` runs one tier while developing.
- `node dist/bin/oma.js --help` smoke-tests the compiled CLI when a compatible `agy` executable is available.

## Coding Style & Naming Conventions

Use strict TypeScript, two-space indentation, semicolons, and single-quoted strings, matching the existing files. Name classes, interfaces, and types in `PascalCase`; functions, variables, and parameters in `camelCase`; and constants in `UPPER_SNAKE_CASE`. Keep comments concise, in Traditional Chinese, and document relevant design mappings as established in `CLAUDE.md`. Never invoke external commands with shell `exec`; use `spawn` or `spawnSync` with argument arrays. No formatter or linter is configured, so `npm run build` is the required static check.

## Testing Guidelines

Jest with `ts-jest` and the Node environment is the sole test framework. Place tests in `e2e/**/*.spec.ts`, select the appropriate tier, and preserve the `TC-T<tier>-<number>` case naming pattern. Add a regression case for every behavioral fix. Use `e2e/helper.ts` for sandbox isolation and condition-based waits rather than fixed sleeps. There is no numeric coverage gate; a clean full-suite run is required.

## Commit & Pull Request Guidelines

This checkout has no Git metadata, so no historical commit convention can be verified. Use short, imperative subjects, optionally with Conventional Commit prefixes such as `fix: prevent stale lock reuse`. Pull requests should explain user-visible behavior, list validation commands and results, link relevant issues, and include terminal output for CLI changes. Highlight changes to rollback, process spawning, locking, or runtime-state formats.
